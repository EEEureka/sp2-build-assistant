# Component selection and assembly fit

Before choosing hardware, turn the intended aircraft role and user preferences into explicit requirements: propulsion family, mounting location, size/clearance, necessary companion parts, and control inputs. Do not choose a convenient template merely to exercise an API.

1. Use catalog categories/subcategories and native descriptions to compare candidates. `partTypes` lists distinct types, not assembly size or all roles. A player's part name does not establish its function.
2. Read `catalog schema` → `data.templates[].parts[]` for the candidate. Count actual parts and inspect each type, original transform, modifiers, defaults and inputs. A turboprop contains a turbine, transmission and propeller as well as a nacelle; its `Engine-Jet-Shroud` type does not make the whole assembly a jet engine. A propeller's style label also does not determine aircraft role. Preserve native companion parts and connections.
3. Rated power or thrust parameters are configuration evidence, not a guaranteed aircraft performance result. Do not compare horsepower with newtons. Report unknown unit or performance conditions instead of inventing equivalence.
4. Before installation, plan where the root will go and what must clear the host, fuselage, wheels and ground. A connection does not align parts or establish a proper physical installation. Rotating parts need clearance for their swept volume, not only the stationary blade pose in one image.
5. Add with a guarded checkpoint, then independently inspect the complete assembly, input configuration, mount/root contact and joint front/side/top views. Check actual geometry/rays and native mechanical links before removing the old assembly. Re-read IDs and center changes after replacement. Unsupported procedural sizing is not permission to substitute arbitrary Part.scale.

Example from a real build: the catalog explicitly offered `Military Jet Engine`, plus Small/Medium/Large Turboprop under `Aircraft Propulsion / Turbo Props` with native descriptions. Choosing the military jet for a user who wants wing-mounted turboprops is a selection error; the existing catalog already distinguishes these options. Use that information before construction. Current template schema is not a pre-placement mesh preview; only after placement can parts.geometry/visual.capture verify real geometry.

After long edit batches and undo/recovery, check the actual designer window as well as tool-generated views. DLL 0.4.10 status includes `sceneIntegrity`; a healthy serialized snapshot alone cannot rule out stale visible aircraft instances. Stop dependent edits when sceneIntegrity is inconsistent. Numeric IDs from a stale selected scene object must never be applied to the current aircraft.

With DLL 0.4.11+, use `designer capture` for native scene/material inspection and diagnostic screenshots. Inspect each `inputControllers[].name/description` before choosing a binding: a propeller's manual pitch and reverse-thrust controls are different from the turbine's throttle. If the intended aircraft does not use a template's auxiliary control, explicitly configure its neutral output instead of inheriting a surprising VTOL mapping.

For retractable landing gear, inspect the template's `Animator.State` keyframes as well as its description and LandingGear input. The presence of an animator or an `End` keyframe alone does not prove two distinct poses exist: the native Aero template examined in 0.7.8.103 has only End, while Wing has two endpoint keyframes. Confirm current template state, then inspect both actual native previews. Preserve existing keys and inputs when refining dimensions; do not invent animation edits through unsupported raw fields. A piston uses its own extension configuration in the designer, so a gear timeline does not by itself prove piston travel.
