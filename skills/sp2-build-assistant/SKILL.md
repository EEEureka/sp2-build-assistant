name: sp2-build-assistant
description: Assist building the aircraft currently open in SimplePlanes 2 using the local sp2build CLI. Inspect native designer views and centers, discover effective component properties, precisely edit shapes, materials and local groups, measure seams and clearances, and undo or roll back edits.
---

Use the globally installed `sp2build` command. All commands return UTF-8 JSON; check `success`, task state, and the shell exit code. The agent needs command execution on the player's Windows machine. This skill does not install or start the game automatically.

For mass/lift/thrust centers, layout, contribution analysis, or before/after center comparisons, read [references/centers.md](references/centers.md). DLL 0.4.0 adds `sp2build craft centers` with optional images from the same sample. Native designer CoL is not the neutral point; these reports do not determine flight stability.

## CLI entrypoint

Use `sp2build ...` for every tool call. Do not invoke `sp2build.py` with `py -3` or `python`, or search the repository or an agent app's cache for a substitute entrypoint. The installed command selects its own Python runtime internally.

First run `sp2build version --json`. If the command is missing in an already running Windows harness, refresh its shell PATH from the registered user PATH while retaining the existing process PATH, then retry:

```powershell
$sp2UserPath = [Environment]::GetEnvironmentVariable('Path', 'User')
if ($sp2UserPath) { $env:Path = $sp2UserPath + ';' + $env:Path }
sp2build version --json
```

The default launcher is `%USERPROFILE%\.sp2build\bin\sp2build.cmd`; the app is in `%USERPROFILE%\.sp2build\app`. PATH changes in one shell do not persist into a separately launched tool shell: repeat the refresh in that shell or restart the harness from a terminal with the updated PATH. If the command still cannot be found, report the CLI installation problem rather than switching to the Python source. Skill import alone does not install the CLI.

## Building workflow

For detailed modeling, cockpit windows, decals/materials, mechanical assemblies, local coordinate edits or iterative fitting to a reference, read [precision building](references/precision-building.md). DLL 0.5.0 adds effective-property discovery, native property adapters, craft-local materials, rigid groups, projector poses, mesh measurements and repeatable native views. Check loaded releaseStatus and the acceptance report; development support is provisional. Use the read → small edit → fixed-view inspection → measurement → diff/recover cycle, with explicit tolerances and a stopping rule.

For choosing engines, landing gear or other assemblies, read [component selection](references/component-selection.md) before adding hardware. Match the user's intended role, native category/description, assembly contents and installation clearances; do not choose a template only because it is easy to call. DLL 0.4.10 `designer status.data.sceneIntegrity` audits current and leftover aircraft instances. An inconsistent scene blocks writes and mesh-analysis captures and requires investigation; part count and exported meshes alone do not prove the live viewport is clean. DLL 0.4.11 `designer capture` permits native scene screenshots for diagnosis even when this check fails.

For the player's camera viewpoint, native appearance, selectable orthographic/perspective views or scene discrepancy checks, read [designer screenshots](references/designer-screenshots.md). `sp2build designer capture` preserves the native scene/materials and restores the player's camera after capture. Menus/cursor/separate gizmo cameras are excluded. Open returned images before claiming visual inspection; use `visual capture` for isolated geometry/ID picking.

With loaded DLL 0.3.2+, prefer `sp2build connections list --view structured`, `sp2build variables list --view structured` and `sp2build outputs list --view structured`. Connections become typed rows with `partA/partB/attachPointsA/attachPointsB`; setters become indexed rows with `variable/function/priority/activator`. Both output-source lists use `sources[].modifiers[].definitions/bindings` and include only parts with output definitions. `data.view` identifies the response shape; schema `data.oneOf` documents both. Omitting `--view` preserves legacy XML/field names. Use the legacy view when you need native fields absent from the projection.

Use `sp2build --help` for global and contextual flags, or `sp2build parts get --help` / `sp2build visual capture --help` for command-specific arguments. Help is offline. Shortcut writes such as `connections connect` require an input JSON file with a nested `operation`; their operation fields are not direct CLI flags. Full input/output contracts remain available through `commands schema`.

For appearance, shape or spatial comparisons, read [visual inspection](references/visual.md). If the loaded DLL advertises `visual.capture`, request a joint view of the relevant groups and actually open the returned `recommendedImages` with the harness image tool. Images use the game's mesh geometry with analysis colors, not native paint/materials. A file path in shell output does not mean the model has seen the image. Report a missing vision input capability rather than claiming visual inspection. Keep independent groups together in the joint view; detail views use a different scale.

Edit only the aircraft currently open in the designer. When the task authorizes navigation, DLL 0.5.0 can enter the designer, load a named native saved craft, select a part, return to the menu and quit through `designer control`; read [native navigation](references/designer-navigation.md). Query `designer status.data.designerControl.available` first. `designer crafts` exposes saved-craft metadata only; edits still require native loading and fresh session/revision. Older loaded DLLs need the player to open the intended aircraft. Do not read or modify saved-aircraft XML directly.

CLI 0.3.1 provides typed output schemas: `sp2build commands schema --command parts.get` describes `data.part`, attach points and units. `commandDetails[].operationKind` maps CLI names to batch kinds; use `--operation connection.connect` for the operation object, and `--command connections.connect` for the CLI envelope. Check `entityKind`; an operation kind is not necessarily an executable command. Instance `name` is editable and non-unique; use `type` for native part type, not names such as “Inboard Pylon”.

Use command-specific help/schema for legal flags. CLI 0.4.3 diagnoses an unknown valueless flag as unknown, without implying it exists. `craft centers` has no `--include-disconnected`: its declared native scope remains unchanged. Finding “disconnect” in the global command list does not establish such an option.

`designer.status.commands` advertises bridge identifiers, including mutation handlers such as batch.apply/undo/rollback. It is not a read-only list or the complete CLI inventory. Discover shortcut aliases and local/task commands with `commands list`; shortcut edits are translated into batch.apply. CLI 0.4.1 adds style-specific shape write schemas and a case-sensitive family enum (`fuselage`, `wing`, `controlSurface`). Choose the family/style matching shape.get; fuselage patches edit existing slices, while replaceSections is supported for wings only.

Part IDs can be reused. Bind cached observations to their session and revision; after edits or recovery re-read affected IDs, never combine old IDs with a freshly fetched revision without checking their identity. DLL 0.3.1 reports `reusedPartIds`. Once a part is deleted in a batch, its numeric ID and old temporary binding cannot target a replacement; use the replacement's new `temporaryId` in subsequent operations. See [edits](references/edits.md).

Inspect `sp2build capabilities --json`, then `sp2build craft snapshot --json`. Reuse the returned `data.identity.craftSessionId` and `revision` for writes. Query `sp2build commands list` and `sp2build commands schema --command batch.apply` for the installed contract.

Snapshot XML preserves native fields unchanged. Its Aircraft `size/boundsMin/boundsOffset` are save-time metadata and can lag current geometry. Use `parts geometry` or a same-revision visual manifest for current bounds; DLL 0.4.4 adds `xmlMetadataCaveat` when XML is requested.

Catalog queries cover parts absent from the current aircraft. Use `sp2build catalog categories`, `sp2build catalog subcategories --category "Aircraft Propulsion"`, and `sp2build catalog list --category "Aircraft Propulsion" --subcategory Jets`, then `sp2build catalog get --id TEMPLATE_ID` and `sp2build catalog schema --id TEMPLATE_ID`. Categories and descriptions come from the game. Template IDs differ from live part IDs. `sp2build parts get --id 123` reads actual current values. `sp2build knowledge catalog` and `sp2build knowledge funky` read the bundled versioned references offline; use runtime catalog/schema for current availability or Mod differences.

Write a UTF-8 JSON input file for complex edits and expressions; do not build shell quoting around raw XML or Funky Trees. Use a batch with a fresh `requestId`, current session and expected revision. Read [references/edits.md](references/edits.md) when preparing edits or recovery; it lists the fuselage cross-section attributes that are writable without native metadata. `batch preview` only checks request structure in v0.1; applying performs the native validation.

For control-surface roles or other input bindings, DLL 0.4.8 adds validated `InputController.State` edits through `part.update`; read the Input controllers section in [references/edits.md](references/edits.md). Discover supported fields in `data.inputControllerEditing` from designer status and `data.templates[].parts[].toolEditableExtensions` from catalog schema. DLL 0.4.9 adds typed `inputControllers` to part/shape/template readouts, including effective defaults and indexed paths. Geometry alone does not determine a control's input: verify its actual axis, mapping and activation group.

For questions about “this selected part”, first call `sp2build designer selection --json`; null means no current selection. Inspect connection `role`, `roleSource` and `jointAxisLocal/World` before attaching a rotator or hinge. These axes are dimensionless directions (not Euler angles), in part-local/world coordinates respectively; `normal` is part-local. All are returned without normalization, so do not assume unit length. The driven connection is identified from native metadata, not its apparent position.

Connections describe native attachment topology. `connection.connect` does not perform general snap-to-attach-point positioning: place ordinary stores with `part.add` position/rotation or separate `part.update` pose changes. A nonzero attach-point gap can be intentional. Native modifier callbacks may adjust specialized parts, so read back the pose. For “under which wing” or other spatial questions, use `parts geometry`, transforms and `designer raycast` in an explicitly chosen direction; BFS proves graph connectivity, and a ray proves an intersection, neither proves physical support or load-bearing ownership.

Connection creation is directed: partB's attach point must receive partA's seek type. Stored `connections list` A/B order does not establish that direction. For example, attach a control surface to the wing's surface receiver, not the wing receiver to the control. Inspect `connections points` availability and type masks before reconstructing edges. Newer 0.5.0 development builds return `invalid_connection` details with both endpoints, rejection reasons and `reverseDirectionCompatible`; this last flag only checks type compatibility and does not guarantee reversed creation succeeds.

For a fuselage/cone with `autoResize:true`, connection can copy the neighbour's sections/length and align the part, then reset the flag. If dimensions were configured manually, explicitly set `shape.update.patch.autoResize:false` before connecting. Typed shape edits do not implicitly disable it. Re-read both shape and pose after native connections.

Default `part.delete` removes one part (plus explicit symmetric peers), leaving independent connected components. With DLL 0.2.2+, inspect `sp2build parts assembly --id ROOT_ID --json` before using `assembly:true`; only a procedural missile's native subparts or a JWing's native control surfaces belong to this scope. Pylons, neighbouring craft parts and arbitrary graph branches are excluded. Unknown/shared ownership is rejected. Check the loaded DLL version using `designer status` when CLI and DLL versions differ; installing the new CLI alone does not activate assembly deletion. See [references/edits.md](references/edits.md) for the payload.

DLL 0.3.1 raycast hits include `part:{id,type,name,typeName}` and `query` semantics. Results contain all eligible collider intersections along the bounded ray, sorted by distance, without a plugin hit-count cap. Multiple colliders can produce repeated part IDs. Unity can omit a collider containing the ray origin. On older DLLs, join IDs against a snapshot from the same revision instead of fetching every hit separately.

For complex shapes, read [references/complex-shapes.md](references/complex-shapes.md), then `sp2build shape get --id ID` and `sp2build shape schema --family fuselage` (or wing/controlSurface). Prefer `shape.update` over raw XML changes for supported families. `sp2build knowledge complex --family landingGear` lists all catalog/source parameters, including unused parts; inventory-only families do not imply typed write support.

Submit `sp2build batch apply --input batch.json --json`. A batch runs its ordered operations with one initial revision guard and one final commit/undo step; it does not increment revision for every operation. On an execution failure the bridge attempts to restore the entire pre-batch snapshot, including earlier operations; verify `rollbackResult.restored`, since recovery can itself fail. A no-op need not increment revision, and a failed native reconstruction can still change its fingerprint. Successful requests return actual changes, real new part IDs, and a before-checkpoint when capacity allows. Re-read affected parts, connections and variables. From 0.2, rebuilds wait for native geometry, recook physics and rebuild editor caches, retaining the primary selected part when it still exists. `parts geometry` and `designer raycast` inspect bounds and actual physics hits. A stale appearance/picking region is a defect: inspect the result and geometry, or use guarded `craft.refresh`; do not claim the tool cannot update an open aircraft. Replacing the plugin DLL itself still requires a game restart.

Completion identity/validation describes that sampled state, not a promise that revision stays unchanged. Native save with AutoRecenter may later translate the entire aircraft and record `Craft Repositioned` in `craft history`'s `data.nativeSteps`; `data.operations` lists bridge mutations. A history label does not distinguish automatic save from player save. On revision conflict re-read/replan; for geometric checks use current transforms and a consistent revision, and compare relative layout to distinguish translation from reshaping. Never infer absence of player edits from empty selection.

`shape.update` follows enabled native symmetry groups by default; opt out with `symmetric:false`. Inspect `symmetry get`, and use link/unlink/create/enable to configure groups. Raw `part.update` requires explicit `symmetric:true` to propagate supported attributes; raw transform propagation is rejected. Do not infer groups merely from spatial proximity. Attribute paths are relative to Part with zero-based repeated child indices.

DLL 0.4.4 derives `symmetry get.configuration` from the current main-control pose and native mirror offset without modifying the game. `nativeCacheStale` and `nativeCachedFrame` expose a saved/recentered aircraft's obsolete native cache; guarded edits refresh that cache before each operation. The plane equation is `dot(normal, position) + distance = 0`: for normal `[1,0,0]`, plane X is **minus** `mirrorPlaneDistance`. Do not use whole-aircraft bounds center as the symmetry plane. `symmetry.create` creates transformed peers and their group; explicitly inspect/connect each new part to its intended host. With older DLLs, a stale native plane can produce an incorrectly placed first copy; stop dependent edits and report it rather than treating a second successful attempt as a fix.

On `revision_conflict` or `session_conflict`, read the current state and replan. On `wait_timeout` or interrupted execution, query `sp2build operation status --id OPERATION_ID` or `sp2build operation wait --id OPERATION_ID`; keep `--instance PID` when multiple games run. Reusing the same requestId with identical content retrieves the same task; do not create another request ID until the original outcome is resolved. Process termination does not cancel an executed edit.

Before a longer sequence, create a checkpoint using a JSON file containing current session, revision, requestId and optional name: `sp2build craft checkpoint create --input checkpoint.json`. For recovery, use `sp2build craft undo` or `sp2build craft rollback` with fresh identity and an explicit target. Checkpoint IDs expire when the player changes craft or restarts the game. Native undo follows player and agent history in time order; inspect `sp2build craft history` before undoing. Rollback can discard intervening edits, so report its full effect. A failed batch reports `rollbackResult`; if recovery fails, stop dependent writes and report the observed state.

DLL 0.5.0 preserves the current craft session and checkpoints across the player's native Undo/Redo. Re-read revision after either action. Loading even the same named, identical saved aircraft creates a new session and invalidates the old checkpoints. Native Undo does not clear a prior `stateUncertain` failure; use verified recovery before further writes.

Variable setters use zero-based indices and preserve order. `variable.reorder.order` lists ALL old indices in the desired new sequence: `[2,0,1]` moves the old third setter first. It is not a list of destination positions or swap pairs; each integer must occur exactly once. Output bindings use native output IDs and modifier state names from `outputs list`, not UI labels. Expression validation compiles against the current context without evaluating flight behavior. Native metadata can omit undocumented fields; report an unsupported field rather than editing around the CLI.

Revision tracks serialized content, not the count of successful edits. A failed batch can advance revision when native recovery changes Euler serialization within the allowed tolerance. Do not reuse the pre-failure revision; use the failure's top-level `identity` or fetch fresh status. DLL 0.3.2 also returns `rollbackResult.beforeRevision/currentRevision/revisionChanged`. Guard/input rejections before mutation need not change revision; not every failure increments it.
